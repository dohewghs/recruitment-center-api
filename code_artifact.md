# 🛠 Серверна частина (Backend) — Проєкт «Рекрутинговий центр»

Цей документ описує технічну архітектуру серверної частини (REST API), актуальні маршрути для взаємодії з клієнтським вебзастосунком (Frontend) та вимоги щодо подальшого розширення API (додавання/редагування даних).

---

## 1. Обрані технології (Стек)

Серверна частина реалізована в межах **PERN-стеку** (PostgreSQL, Express, React, Node.js):

* **Середовище виконання:** Node.js
* **Фреймворк:** Express.js (маршрутизація та створення REST API)
* **База даних:** PostgreSQL (хмарний хостинг **Neon.tech**)
* **Хостинг API:** **Render** (налаштовано автоматичний деплой із GitHub)
* **Основні бібліотеки:**
  * `pg` — драйвер для підключення та виконання SQL-запитів до PostgreSQL.
  * `cors` — дозвіл крос-доменних запитів для взаємодії з Frontend.
  * `dotenv` — безпечне зчитування змінних середовища (конфігурацій і паролів).
  * `nodemon` *(dev)* — автоматичний перезапуск сервера під час локальної розробки.

## 3. Підключення до Бази Даних

Підключення до хмарної БД PostgreSQL на **Neon.tech** реалізовано через драйвер `pg` із використанням захищеного рядка підключення (`DATABASE_URL`):

1. Конфіденційні дані (логін, пароль, хост) зберігаються локально у файлі `.env` (ігнорується Git), а на продакшені — в **Environment Variables** на Render.
2. Сервер зчитує `DATABASE_URL` на самому старті за допомогою `dotenv`.
3. Налаштовано обов'язкове SSL-шифрування (вимога сервісу Neon).

## 4. Контракт взаємодії з Frontend (Параметри та Відповіді)

### Як передавати параметри з Frontend
1. **Query-параметри (`req.query`)** — використовуються для фільтрації та параметризованих `GET`-запитів.
   * *Приклад:* `/api/recruits/missed-sessions?title=Базова військова підготовка&n=2`
   * *Рекомендація для Frontend:* формувати параметри через `new URLSearchParams(...)`, щоб кирилиця та пробіли гарантовано коректно кодувались.
   * *Гнучка типізація:* для окремих маршрутів (наприклад, пошук за центром) бекенд автоматично розпізнає, чи передано числовий ID, чи текстову назву.
2. **Параметри шляху (`req.params`)** — для звернення до конкретного запису за ID (наприклад, `/api/recruits/10`).
3. **Тіло запиту (`req.body`)** — зарезервовано для майбутніх `POST` / `PUT` запитів (передача JSON-об'єктів).

Усі параметри передаються в PostgreSQL виключно через параметризовані запити (`$1`, `$2`, ...), що повністю захищає базу даних від SQL-ін'єкцій.

### Формат відповідей та коди стану
API працює виключно у форматі **JSON**. Усі відповіді формуються централізовано через `executeQuery.js`:
* `200 OK` — запит успішно виконано, у тілі відповіді повертається JSON-масив рядків (`result.rows`).
* `400 Bad Request` — не передано або некоректно передано обов'язкові параметри (`{ "error": "..." }`).
* `404 Not Found` — маршрут або запис не знайдено.
* `500 Internal Server Error` — внутрішня помилка сервера або БД.

## 6. Майбутній функціонал: запити на додавання даних (`INSERT` / `POST`) - до обговорення

Архітектура сервера вже готова до розширення під операції запису (`POST`, `PUT`, `DELETE`) — у `index.js` підключено `express.json()`, а шарова структура дозволяє додавати нові SQL-файли без зміни існуючої логіки. Конкретний перелік форм буде узгоджено командою на наступному етапі.

### Очікування бекенду від фронтенду для майбутніх `POST`-запитів
Щоб інтеграція форм додавання пройшла без помилок, фронтенд має дотримуватися таких правил:

1. **HTTP-метод і заголовки:**
   * Використовувати метод `POST` (для створення) з обов'язковим заголовком:
     `Content-Type: application/json`
2. **Формат передачі даних (`req.body`):**
   * Дані надсилаються у тілі запиту у вигляді JSON-об'єкта.
   * Назви ключів мають відповідати погодженим полям схеми БД (у `snake_case`, наприклад `full_name`, `birth_date`, `center_id`).
   * **Формат дат:** стандарт `YYYY-MM-DD` (наприклад, `"2026-05-15"`).
   * **Числові ID та кількості:** передавати як числа (або валідні числові рядки).
3. **Обробка відповідей сервера:**
   * При успішному створенні сервер повертатиме статус **`201 Created`** та JSON щойно створеного об'єкта (завдяки `RETURNING *` у PostgreSQL), щоб фронтенд міг одразу оновити UI без повторного `GET`.
   * При помилці валідації (порожні обов'язкові поля, неіснуючий зовнішній ключ) сервер повертатиме **`400 Bad Request`** або **`409 Conflict`** із полем `error` для відображення користувачу.
